# Stage 3: routing and pinned catalogs

This profile extends the desktop host described in [stage2-contract.md](stage2-contract.md). Its source authorization, immutable storage, token serialization, recovery, failure envelopes, and stated app limitations still apply. New desktop runs use `stage3`; the operator can run `--profile stage2` for the extraction acceptance suite. Existing schema-1 runs written by 0.2.0 keep their profile, instructions, limits, and stopping point. There is no migration or reopening of a completed run.

The public task is **verify this skill**. Extraction, classification, and lookup are internal operations. This release finishes a routing checkpoint, not a scientific verification: `verification_complete` remains false, and it produces no verdict or evidence grade. The repository document `reviews/PROJECT-COMPLETION.md` names the subsequent work.

## State and tool protocol

The Stage 3 matrix in [workflow.md](workflow.md#stage-3-profile) is authoritative. The existing three extraction tools keep their request schemas. Every routing request also requires `run_id` and the latest `state_token`.

- `list_claim_types`: no additional parameters. Returns the pinned reviewed index, its digest and revision. All claims must still be in `routing`. It records delivery of that exact index; repeated reads are allowed within the step budget.
- `commit_claim_type_assignments`: `manifest_id`, `index_digest`, and `assignments`, exactly one per claim. Each supplies `claim_id`, `claim_type_id`, `proposal`, and `report_note`. For an existing type, `proposal` is an empty object; for a new type, `claim_type_id` is empty and `proposal` contains nonempty `name`, `definition`, `inputs`, `outputs`, and `boundaries`. A proposal receives a content-derived ID and remains provisional. Semantic equivalence and applicability are Claude's responsibility, not a keyword classifier. Return all routes and move all claims to capability selection atomically. Reject missing, duplicate, unknown, stale, or undelivered references without partial route writes.
- `find_registered_evaluators`: `claim_id`, `route_id`, `scope`, and `intended_grade`. Scope must exactly equal the committed claim scope. The configured target is A; callers cannot change it. One claim is selected per request. Python searches A through D, requiring an exact declared scope and type match, compatible interfaces, and validated registry status. At each grade a registered evaluator takes precedence over a generic harness; a complete pair is required for A-C. Documentary D uses `subject_runner: not_applicable`. A missing runner can never disqualify D. All matches at the strongest eligible grade are returned, with exact entry digests and versions. Provisional/retired entries are never matches. Missing implementations and missing runners produce distinct claim-local operational records; other claims continue.

Selections are capability descriptions, not execution authorization or evidence. A-C harnesses carry separate scoring, aggregation, configuration and trial-policy identities; D carries rubric and independent-assessor contracts. The later planning/audit implementation must validate these before any execution. Python cannot establish scientific fitness from registry metadata alone.

An empty claim manifest completes Stage 3 immediately. Otherwise it completes when every claim has a saved selection: matched claims retain `planning` as a future state, unmatched claims are `terminal_operational`. The run closes at `stage3_complete` with no further workflow tools. Run failures and cancellation close at `incomplete`. The run step limit is 256; other Stage 2 limits remain unchanged.

## Catalog releases and trust

Selection responses are bounded to 16 compatible pairs in stable ID order. They report the total compatible pair count and whether further pairs were omitted, with distinct capability and runner contracts included once. Lookup still searches the full pinned catalog for the strongest eligible grade.

The operator supplies a catalog, never the submitted skill or a tool-call argument. The default is the repository's bundled reviewed registries. Those registries are currently empty. Proposed seed material under `examples/catalog/` is test data and is never loaded by default or published as reviewed.

A release directory contains `manifest.json` and three JSON assets: `claim_types.json`, `evaluators.json`, and `subject_runners.json`. Manifest schema 1 contains `catalog_version`, integer `runtime_interface` and `skill_interface` (both 1), nonempty `provenance`, and `assets`. Each asset has `path`, `version`, `sha256`, and `bytes`; asset keys are the three registry names. No arbitrary asset paths, executables, archives, URLs, or installation hooks are accepted. Evaluator resource dependencies are metadata pins (`id`, `version`, `sha256`); Stage 3 does not download scientific resources or grant execution permission.

Each registry includes an integer schema and nonnegative revision. Claim types use schema 1; evaluator/harness registry schema 2; subject runners schema 1. Entries have distinct `id`, `version`, and `status`; their digest is computed from canonical JSON. Claim types additionally have name, definition, inputs, outputs, boundaries, and provenance. Capabilities declare claim-type IDs, exact supported scopes, grades, interfaces, resource pins, limitations, provenance, and the appropriate execution/documentary contracts. Runners declare interfaces, bounded configuration, and provenance. Unknown schema/interface, malformed data, duplicate IDs, unknown type links, and asset digest/size mismatches fail closed. An empty registry is valid; missing or corrupt assets are not an empty successful search.

`scripts/catalog_release.py` builds a deterministic release from an explicitly named directory. Building does not attest maintainer review or publish anything. Human review and an authorized commit remain prerequisites for promotion to `registry/`.

`scripts/catalog_release.py fetch` retrieves a release from the existing `njdjyxz/sci-ai-verifier` GitHub repository at an operator-supplied full 40-character commit SHA. The operator also supplies the expected manifest SHA-256 from the reviewed release. The fixed repository, exact commit, fixed asset paths, HTTPS, denied redirects, bounded responses and timeouts constrain retrieval. Requests use GitHub's [repository contents API](https://docs.github.com/en/rest/repos/contents) raw response format. No credentials or source submission are sent. A self-declared provenance string is not a signature or proof of review; the operator's independently obtained manifest digest and trusted repository commit establish the chosen release.

Verified releases are cached by manifest digest below the configured data directory's `.verifier/catalogs/`. `fetch --offline` reverifies that exact cache and never connects to GitHub. A failed fetch leaves any prior configured selection unchanged; it never substitutes another release or a bundled empty registry. Incompatible content is not an availability failure. The utility activates a release only after every asset validates, using an atomic configuration write. Compatible catalog releases do not require reinstalling the skill.

At start, Python pins the selected manifest and every asset in the immutable object store and records their exact identities in `catalog-lock.json`. Active runs and resume read only these objects; changing installed registries or the configured cache affects new runs only. Unavailable or incompatible configured catalogs create a durable run-level operational outcome before source loading. Tool calls never trigger downloads.

## Routing artifacts and provisional types

The remote fetch path is `catalog/` at the exact specified commit. Cache receipts bind downloaded content to its repository and commit; offline activation and new-run pinning verify the matching receipt. Downloads cap each file at 1 MiB, set socket timeouts of at most ten seconds, check elapsed time between chunks, and check a 30-second budget between requests. A blocking socket read may end after the elapsed-time deadline, at which point the release is rejected.

`routing.json` identifies its source manifest and catalog lock, records the delivered index digest, immutable routes and proposed types, and appends per-claim selections. Each selection includes claim/route IDs, revision, queried scope, original target, outcome, resolved grade/kind, exact capability/runner/resource pins, catalog asset digests, limitations and any operational-outcome ID. It never contains a scientific status or evidence grade. Routing and catalog-lock projections are recoverable from the journal.

Stage 3 narrows the full target's merged runtime registry: proposals remain in their originating run's committed routing object and are projected under `.verifier/registry/claim-types/<run-id>.json` for review. They are not automatically merged into other runs or promoted. This avoids changing another run's pinned taxonomy or claiming an unreviewed contribution is shared scientific authority. Later promotion requires human review. No runtime writes to repository `registry/` exist.

## Acceptance

Automated checks must cover extraction through selection; no claims; correct and incorrect type/scope matches; duplicate, incomplete, stale and undelivered assignments; A-C pairing; registered preference; strongest lower-grade fallback; D without a runner; no capability vs no runner; continued independent claims; catalog incompatibility, corrupt assets, bounded downloads, redirects, exact offline reuse and cache absence; changed release/source during resume; operational outcome persistence; prior Stage 2 compatibility; and a packaged stdio Stage 3 flow.

Live desktop acceptance and scientific review remain separate. Preserve the Stage 2 evidence and its unresolved conversation-only check. Extract `expected_behavior` only from the submitted text: use `Not specified` for absent detail. Do not add scientific definitions from background knowledge, and do not silently rewrite earlier manifests to repair them.
