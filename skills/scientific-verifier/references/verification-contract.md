# Verification profile: complete bounded chemical-mass workflow

This profile extends Stage 3 through planning, locked resources, bundle validation, audit, subject observations, result commitment and reporting. It preserves the Stage 2 desktop-host limits and saved-run compatibility. A completed workflow accounts for every claim; it does not imply that every claim was scientifically evaluated or passed. Empty catalogs produce an honest report of unavailable capabilities.

## Scope and authorization

The initial executable scientific method is the bounded chemical-mass pilot. Installed code is selected by a fixed method key; the agent never supplies code, endpoints, prompt wrappers, expected answers, thresholds or a model configuration. Catalog entries must be reviewed and validated/approved before use. Provisional example entries and synthetic test approvals are never production authority. Maintainer review/publication and live app acceptance remain external evidence, not prerequisites for implementing deterministic modules.

The runtime accepts only installed `chemical_mass_v1` numeric configurations for this profile. It retains exact source, catalog, capability, runner, method, policy and resource identities. Unsupported scientific methods produce a claim-local `implementation_required` record. A documentary method without an independently provisioned assessor records `assessor_unavailable`, never a planner-authored D result. No arbitrary submitted scripts execute in the local extension.

## Tools and state

The verification matrix in workflow.md governs legality. Requests retain `run_id` and `state_token`. All claim-scoped tools require `claim_id`; all plan-dependent requests also require the exact `plan_id` and integer `plan_revision`. Python fills already committed parent references, policy, resource roles and bounded configurations; it does not ask the agent to retype immutable data.

- `commit_evaluation_plan`: selection ID, bounded match index, exact claim scope, trial count, and report note. Python fixes method, resources, model/provider configuration, comparison/aggregation rules and policy before observations exist. A revision invalidates all downstream authority and gets a distinct lock. Returns `resource_resolution_required` until required roles are locked.
- `find_resources`: returns only installed, pinned resources matching the plan's exact resource requirements, with provenance and digests. Missing infrastructure is `resource_unavailable`, not U. This profile does not search arbitrary external resources.
- `materialize_resources`: search ID; Python verifies all required bytes and binds them to this exact plan revision. Partial locks cannot authorize execution. Registered capabilities proceed to audit with their fixed cases; approved generic capabilities proceed to bundle construction.
- `build_evaluation_bundle`: deterministically constructs cases and expected values from the locked reference and case specification, with no caller-provided transformation code. Returns `bundle_candidate_built`.
- `validate_evaluation_bundle`: exact bundle ID; checks nonempty unique cases, finite independently computed expected values, supported scope, input/answer separation and fixed policy. Returns `bundle_adequate` for the supported method; invalid data is an operational integrity failure.
- `register_evaluator`: exact validated bundle ID; persists the bounded configuration as provisional in the run, projected under `.verifier/registry/`. It never edits reviewed registries. Returns `provisional_evaluator_registered` and requires a new registered plan revision before audit.
- `commit_plan_audit`: exact plan and lock IDs plus bounded semantic scope/fairness findings and proposed audit status. The proposal is advisory. Python checks every committed binding, method/policy version, scope, runner contract, resource digest and bundle. Unsupported semantic findings return `plan_revision_required`; integrity failure never passes. Passing audit atomically validates the exact run-local provisional configuration and bundle.
- `execute_evaluation_plan`: exact audit ID and audited request budget. Python obtains each subject observation with expected answers withheld, scores each separately, then aggregates scored trials under the fixed policy. The host-provisioned subject adapter receives only the immutable submitted instructions and case input. Provider identity/configuration is pinned; missing configuration produces an operational outcome. No real API request occurs during synthetic testing.
- `commit_claim_result`: exact execution ID and optional proposed status/grade. They must equal the authoritative execution fields when supplied. The committed result copies provenance, grade-policy inputs, observations, coverage and limitations. There is no grade derived from a successful tool status.
- `write_report_card`: run token; Python derives the complete result/outcome accounting and writes immutable JSON plus Markdown projections. Every claim must be terminal. No overall scientific grade is synthesized.

## Evidence and execution boundary

The fixed policy names supported grades and total eligibility predicates before execution. Missing observations caused by infrastructure failure are operational failure; they are not discarded or treated as scientific failure. Nondeterministic single-trial evidence is capped at C, and C still requires the reviewed independent-comparison design. Agreement measures scored-result consistency, so unanimous failure and unanimous success have the same evidence-strength eligibility. Invalid numeric observations are retained and never silently removed from denominators. This bounded delivery has no independent D assessor, so an unusable completed sample records `assessor_unavailable` directly, with null status/grade and retained evidence. The workflow explicitly specializes the general target's D-replanning branch; no D/U result is invented.

Raw requests and observations are recorded before continuing to the next trial. A request whose response is uncertain after interruption must not be silently retried as if it were the original observation: recovery records an operational interruption with the existing request/observation references and counts recovered attempts against the run budget. This keeps the evidence sample fixed. Python enforces 64 total calls, at most 4096 response bytes, at most 128 KiB of submitted text, and a fixed 30-second deadline passed to the adapter. It rejects a late response after return; an in-process callback is not a hard timeout or sandbox. A future live adapter must independently enforce the deadline and isolation. No provider is implemented or enabled in this delivery, and no API key is needed for the configured fixtures.

## Configuration, compatibility and bootstrap

The command-line default is `verification`; explicit `stage2` and `stage3` profiles preserve their old checkpoints. Schema-1 writers 0.2.0, 0.3.0 and 0.4.0 are supported without migration. `verification_complete: true` means report accounting and finalization finished, including an all-operational or zero-claim report; it is never a scientific pass indicator.

Operators may provide `--subject-fixture <file>` together with a deliberately synthetic catalog via `--catalog <directory>`. Schema-1 replay files contain `model_id` and a formula-to-text `responses` object. Their exact bytes are part of the adapter identity. Each call returns the prescribed text for that formula, including on repeated trials; repetition is a workflow fixture, not independent model sampling. A missing case is operational failure. Keep fixture answer files outside the submitted directory.

Embedding hosts can inject `Runtime(..., subject_adapter=adapter)`. Its identity contains bounded `adapter_id`, `model_id`, and boolean `synthetic`; change the adapter ID whenever implementation/configuration changes. `observe(source=..., case_input=..., config=..., timeout_seconds=...)` returns only `text`, `model_id` and `response_id`. The subject receives snapshot text and formula input only. Adapter exceptions and identity mismatches are operational failures, and arbitrary exception messages are withheld. The default adapter is unavailable. Synthetic catalogs are explicit test inputs and never populate reviewed registries.

Bootstrap supplies the complete skill, this profile, evidence rubric and resource policy, plus explicitly selected common/state/desktop/routing sections of the shared contracts. The compact verification tool/artifact sections replace the general target's richer requests for this profile; every reachable operation is covered. All pins remain immutable on resume. Full target prose about unsupported D/U or external-resource branches need not be included as active instructions.

## Acceptance

Test complete registered and generic-harness flows, immutable plan revisions, stale locks and audits, source/resource mutation, unsupported methods, missing runners/assessors, wrong and correct outputs, invalid/missing observations, separate trial scoring, grade/status non-equivalence, no-result operational reports, zero claims, mixed claims, interruption/cancellation, exact parent checks, legacy profile recovery and both report formats. Synthetic tests are labeled as such. Live app behavior, actual provider/model identity and independent scientific approval must be recorded separately before release acceptance is complete.
